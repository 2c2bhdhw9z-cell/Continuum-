## 1. The two-phone Game Boy link cable: the app's half (Built, untested)

What a player gets: two phones, each playing a Game Boy or Game Boy Color game on cBoy, joined by
a link cable over Wi-Fi. Each phone plays its own game and keeps its own save, so the games can
differ (Pokemon Red trades with Blue), which is what makes this a cable and not the shared-game
online play the app already had.

How a player starts it: the same way as online play. In the game's … menu the row reads **Link
cable to a second phone** (instead of "Play online with a second phone") whenever the game is a
Game Boy game on cBoy. One phone taps **Wait for the other phone**, the other joins by the address
shown or picks it under Nearby. The line at the top then says **Link cable plugged in (ping 12
ms)**. A Game Boy game on mGBA keeps the old shared-game sheet, with one extra line saying that
switching Game Boy games to cBoy in Settings, Cores turns it into a link cable.

The plain lines a player can see, all of them from the engine:

- the other phone is not on cBoy (or not on a Game Boy game): **Link cable unplugged: the link
  cable needs a Game Boy game running on cBoy on both phones** (the same words on both phones, so
  they name neither);
- the connection drops: **Link cable unplugged: the connection to the other phone dropped** (the
  network's own error text is kept out of it, and goes to the log);
- nothing heard for ten seconds: **Link cable unplugged: nothing heard from the other phone for
  10 s**;
- the other player leaves: **Link cable unplugged: the other player unplugged the cable** (or
  "went back to the library");
- two different cBoy versions: **...the two phones have different versions of cBoy, so put the
  same Continuum build on both**.

What was built:

- **The engine answers cBoy's call for the cable** (libretro's `SET_NETPACKET_INTERFACE`, 78), in
  `crates/emulator-bridge/src/cores/native_core.rs`, and keeps the core's six callbacks and its
  protocol name (`cboy-link-1`) on the core object. Two copies of a core on one thread never mix
  their blocks, which is what let the test below run two cBoys in one process.
- **A second kind of online session**, `Mode::Link`, in `netplay/session.rs`. The running core
  decides it on each phone: a core that offers a cable gets a link, everything else the old
  shared game. A link sends no starting state and runs no frames in step; the handshake only
  checks that both phones speak the same cable, and then cBoy's three-byte blocks cross as they
  are, in order, never looked inside.
- **The three calls cBoy asked for**, all from the engine's tick, between frames, on the thread
  that runs the game (libretro's rule): `start` when the two phones agree (0 on the host, 1 on
  the other phone), `receive` for every block before the next frame, `poll` after every frame,
  and `stop` exactly once when the session ends, however it ends (left, dropped, timed out, game
  closed). A dropped connection is noticed on the network's thread, but the cable only comes out
  on the next tick.
- **Time stands still while the cable is on**, as libretro asks of a frontend: rewind, fast
  forward, loading a state, reset, changing cheats and everything else online play already
  refuses is refused here too (the refusals that give a reason say "... is off while the link
  cable is on"), and the player hides the same buttons it hides for online play. The game keeps
  running at its own pace; a paused phone still answers the other one, so a pause is not mistaken
  for the connection dying.
- **This phone's saves stay on while linked.** The shared game switches the joining phone's
  in-game saves off (the host's game replaced its own). A link replaces nothing, so they stay on:
  a Pokemon traded in reaches the save file. This was the one place where reusing the old flow
  as it was would have lost a player's progress.
- **The online version went from 1 to 2**, because the joining phone now always says which cable
  it has straight after hello. `Hello` itself kept its old shape, so an older Continuum build
  still reads a newer phone's hello and refuses it in words ("the two apps speak different online
  versions (1 and 2); update both") instead of choking on it. That means **a phone on this build
  cannot play online with a phone on an older build**, shared game or cable, until both are
  updated.

### What the tests prove

- **Two engines, each with its own copy of a host build of cBoy, loaded through the real libretro
  entry points and joined by the session's cable in one test process**
  (`two_phones_link_two_cboys_through_the_real_entry_points` in `netplay/bridge_glue.rs`). Phone A
  drives the cable (internal clock) with `$11` and reads B's `$22`; then B drives with `$44` and A,
  waiting on the external clock, reads it while B reads A's `$33`. Every block crossed: two each
  way. Then the connection goes quiet and A drives `$55` into it: the game waits (still nothing
  after five frames), gives up after 8 frames, reads `$FF` like a pulled-out cable, and carries
  on. Ten seconds of nothing later both sessions end on their own clocks and cBoy's cable is
  really unplugged: a byte driven after that finishes at once, as on a console with nothing
  attached. Passed five runs out of five, identically (25 rounds for both directions). It is
  opt-in, like `tests/cboy_frontend.rs`, because the bridge's test run does not build cBoy:
  `cargo build --release --manifest-path cores/continuum-gb/Cargo.toml`, then
  `CBOY_SO=$PWD/cores/continuum-gb/target/release/libcontinuum_gb.so cargo test -p emulator-bridge --features native-core --lib two_phones_link`.
  Without `CBOY_SO` it says it was skipped and passes, so CI does not run it.
- Two engines with a test core on a cable (always run): each runs its own game (the two machines
  stay different, nothing replaced the joining phone's), the cable goes in once on each with the
  right numbers, more than a hundred numbered blocks cross each way whole and in order, a phone
  paused for fifteen seconds keeps the session alive and gets every held block when it resumes,
  the refusals read the link sentence, and leaving pulls both cables out.
- A dropped connection pulls the cable out on the next tick and not from the network's thread, and
  closing the game pulls it out before the core goes.
- The session on its own: two different games join; a phone without the cable is refused on both
  sides in the same plain words, whichever side it is on; two cable versions are refused; an app
  from before the cable is refused on its version without being left waiting; a dropped
  connection, a timeout and the other player leaving each unplug exactly once; a cable that never
  went in is not pulled out; shared-game messages on a cable and cable blocks in a shared game are
  both refused as a broken peer; a peer that never stops sending is held to a bounded queue; every
  link state has its own line, none of them starting "online:".
- The wire: the three new messages round-trip, a block over the cap is refused before it is
  buffered, and the old `Hello` is checked byte for byte so its shape cannot drift.

### What was not proved, and needs two phones

- Real Wi-Fi between two iPhones, and whether a real Pokemon trade or a Tetris match goes through.
  A byte crosses on the frame boundary, so a round trip is about two frames plus the network
  (about 33 ms plus ping); a trade has no deadline and should not notice, a fast two-player game
  may feel loose. Nothing here measured that, because it cannot be measured without two phones.
- That cBoy's timing suits real games' link handshakes (Pokemon's, Tetris's). The test cartridge
  above is ours; no commercial link game was run.

### Handed on to cBoy (its files, not changed here)

- **The "Link cable" setting's description still says "Linking two phones is not available yet."**
  (`cores/continuum-gb/src/options.rs`, `cboy_link`). That sentence is now false and has to go;
  something like "To link two phones, open the … menu in a game and choose Link cable." would say
  how. Nothing else in the setting needs to change: the cable comes from the app's session, and
  "Unplugged" stays right until one starts.
- **Mid-frame reading.** The engine hands cBoy a real `poll_receive_fn`, but it has nothing new to
  give mid-frame (every block is handed over just before each frame, and none can arrive during
  one because the connection waits for the same engine lock). If two-phone testing shows fast
  games feel loose, the round trip can only be cut on the app side by delivering during the
  frame, which would mean taking network bytes without the engine lock. Not done: it cannot be
  judged without two phones.

## 2. Mega Drive cartridges that save to a memory chip (EEPROM), and the J-Cart ones (Built, untested)

The item said *Sampras Tennis 96* is the cartridge with the EEPROM. MAME's software list
(`hash/megadriv.xml`, CC0 data; fetched into scratch, not committed) says otherwise: it puts
*Pete Sampras Tennis '96* on the plain J-Cart board, the same one as *Super Skidmarks*, with no
save chip at all. So it got what its board really has: the J-Cart (players 3 and 4), no save.

What changed, all in a new patch, `scripts/patches/blastem-cartridge-saves.patch` (BlastEm's
cartridge list, `rom.db`), applied after the memory patch. Every number in it comes from MAME's
list (the checksum and size of each dump, and its board) or from BlastEm's own entry for the same
game or the same board (the wiring and the EEPROM size); none was guessed.

- **40 cartridge dumps added by their checksum.** BlastEm finds a cartridge's save chip in its
  list by the checksum of the whole game first, then by the product code in its header. It had
  most of these games by product code only, so a dump whose header code it cannot match got no
  save at all, and a cartridge with an EEPROM that BlastEm misses never saves (a header has no way
  to describe an EEPROM). Now every EEPROM and J-Cart dump in MAME's list is found by checksum:
  Sega's own (Evander Holyfield's Boxing, Game Toshokan, Greatest Heavyweights x3, Mega Man: The
  Wily Wars, Rockman Mega World, Sports Talk Baseball, Wonder Boy in Monster World, Monster World
  III, Turma da Mônica na Terra dos Monstros, Dodge Danpei, Ninja Burai Densetsu), Electronic
  Arts' (Bill Walsh College Football, John Madden Football '93 and its Championship Edition,
  NHLPA Hockey '93 x3, Rings of Power), Acclaim's (NBA Jam x4, NBA Jam TE's 2002 fix release, NFL
  Quarterback Club and '96, College Slam, Frank Thomas Big Hurt Baseball, Blockbuster World Video
  Game Championship II) and Codemasters' (Brian Lara Cricket x2, Brian Lara Cricket 96 x2, Shane
  Warne Cricket, Micro Machines 2 x2), plus the two J-Cart-only ones above.
- **Games BlastEm's list did not have at all**, so they never saved before (unless a header code
  happened to match another game's): Shane Warne Cricket, Blockbuster World Video Game
  Championship II, Turma da Mônica, Monster World III (Japan, Korea) and the 2002 NBA Jam TE.
  MAME notes that Turma da Mônica's save fails quietly in MAME itself, so that one is the least
  certain.
- **Three fixes found while checking the list against MAME's:**
  - *NFL Quarterback Club* is one 4 MB chip, but the list only mapped 3 MB of it, so anything the
    game kept in its last megabyte read as rubbish. It is mapped whole now, like College Slam.
  - *Micro Machines 96*'s second dump (MAME's `microm96a`) had its save chip but not its J-Cart, so
    players 3 and 4 answered nothing. It has both now, like the first dump.
  - *Rockman Mega World* comes in two versions with the same product code: one with an EEPROM, one
    with ordinary save RAM. BlastEm gave both the EEPROM. The save-RAM one is now listed by its
    own checksum with no special hardware, so BlastEm reads its save RAM from its header like
    any other cartridge.
- Sizes: where MAME and BlastEm disagree on the chip (MAME says a 24C08 for Micro Machines 2 and a
  24C02 for NBA Jam TE; BlastEm uses 2048 and 512 bytes), BlastEm's existing size was kept, so a
  dump it already knew behaves exactly as before. A bigger chip than the game uses is harmless:
  the game only ever reaches the part it knows.

Not covered, and why: *Pier Solar* (its save chip talks a different protocol and the cartridge
has its own bank switching; BlastEm has neither, so a list entry cannot fix it); the Ninja Burai
Densetsu prototype (MAME does not define its board); the Monster World III and Super Skidmarks
prototypes and the Russian *Tachki* (MAME marks the first as not saving and the other two as
unconfirmed); and the sets MAME keeps as several chips (NBA Jam TE, an NBA Jam prototype), whose
one-file dumps have checksums MAME does not list. NBA Jam TE is still found by its product code
as before.

### What the tests prove

- `crates/emulator-bridge/tests/blastem_rom_db.rs` (runs on every CI build): the new entries parse
  by BlastEm's own rules (its `config.c` parser, line for line: a repeated key, a key with no value
  or an unbalanced brace fails), and each one is exactly what MAME lists for that set (the
  checksum, the ROM size, the EEPROM size, every wire of the board), with each entry's comment
  naming its MAME set; the two fixes are in the patch; and the build applies the cartridge list
  after the memory patch. With `BLASTEM_SRC` set to a clean BlastEm at the pin, both patches apply
  in the build's order and the whole patched list (163 entries) parses with each key once. All
  checked here; a wrong EEPROM size or a wrong wire makes it fail (tried).
- `crates/emulator-bridge/tests/blastem_frontend.rs` (opt-in, `BLASTEM_SO`), with BlastEm built
  for the host from its pin with both patches, loaded through the app's own entry points: BlastEm
  itself reads the patched list (it parses all of it on every cartridge load); generated
  cartridges with Greatest Heavyweights', Micro Machines 2's and NFL Quarterback Club's product
  codes get 128-, 2048- and 256-byte saves; and a 68K program reading NFL Quarterback Club's last
  megabyte gets the ROM's bytes. Against the same build without the new patch that read gave
  `$FFF0FFF0`, so the fix is what changed it.

### What was not proved

No real cartridge was run: the dumps are commercial games, so nothing here can show a real game
writing its save, and the checksum entries can only be checked against MAME's numbers, not against
a cartridge. Whether a given player's file matches depends on it being one of the dumps MAME lists.

## 3. Sega CD: changing discs, and the save cartridge (Built, untested)

What a player gets:

- **A multi-disc Sega CD game plays from its `.m3u` playlist**, and the game's … menu shows **Next
  disc** and **Insert disc...**, the same two controls the PlayStation has. Before, the app quietly
  opened the playlist's first disc and nothing could ever put the second one in.
- **The save cartridge works and is kept.** The Sega CD's add-on save cartridge is now there,
  formatted and empty the first time, and whatever a game or the console's own memory screen puts
  on it is saved next to the game's other save and comes back next time. Before, it was blank
  every time the game was opened.

What was built:

- **A third BlastEm patch, `scripts/patches/blastem-sega-cd-discs.patch`** (BlastEm's libretro
  glue, `libblastem.c`), applied after the other two:
  - it reads an `.m3u` (one disc per line, relative to the playlist; comments, blank lines, Windows
    line ends and an optional `|label` after a disc are all fine) and opens its first disc;
  - it offers libretro's disk control interface (the extended one, or the basic one to a frontend
    that only has that) for every disc game, one disc or many, and to no cartridge;
  - a swap goes through the drive the way a real one does: the tray opens (the drive reports its
    door open), the disc goes in, the tray closes (the drive reports the tray moving for half a
    second), then the drive reads the new disc's table of contents, so a game waiting for its next
    disc sees one arrive. "Next disc" does all three in one tap;
  - a disc that will not open (a missing track file, say) leaves the old disc in and closes the
    tray, instead of the core ending the app, which is what BlastEm's own error path would have
    done mid-game;
  - a save state of a playlist game remembers which disc was in and puts it back when loaded. It is
    a small section in BlastEm's own state format, first in the state; a one-disc game and every
    cartridge get none, so their states are exactly what they were;
  - the save cartridge (128 KB, BlastEm's default) is formatted at start like the console's own
    memory, and handed to the app under a memory number of its own, since libretro's one save
    region is already the console's internal memory.
- **The engine keeps the cartridge as `<game>.bcr`** next to the game's `.srm`, written and read
  with it, the same way cBoy's clock goes to `<game>.rtc` (`crates/emulator-bridge/src/bridge.rs`;
  the number is `MEMORY_SEGACD_RAM_CART` in `memory.rs`). Only BlastEm is asked for it. The sync
  already carries `.bcr` files (it is the name Saturn emulators use for theirs), so nothing in the
  app had to change for it to be backed up.
- **The app no longer swaps a Sega CD playlist for its first disc** (`ContinuumApp.swift`): the
  playlist goes to BlastEm as it is. The disc controls show by themselves, because they appear for
  any game whose emulator offers discs.

### What the tests prove

`crates/emulator-bridge/src/cores/blastem_host_tests.rs` (opt-in, `BLASTEM_SO`): BlastEm built for
the host from its pin with all three patches, inside a real engine session, through the same
engine calls the buttons make. Nobody here has a Sega CD start-up ROM, so the tests give the
console one of their own: six 68K instructions that write two bytes to the save cartridge and
wait. That is enough for BlastEm to build and run the machine, the drive and the cartridge; no
game runs and no real disc is read. Every disc is generated by the test.

- A playlist of two discs opens the first; the disc list is two, with the labels the playlist
  gives (or the file name); **Next disc** answers "inserted Second (2 of 2)", the drive reports the
  tray moving, and 30 frames later reads the new disc (three tracks, against the first disc's
  one); Next disc again wraps to disc 1; **Insert disc...** reaches the same call; a disc number
  past the end is refused.
- A state made on disc 2, loaded while disc 1 is in, puts disc 2 back first. The same state still
  loads in the build from before this patch (it skips the section it has no reader for, and runs
  on), checked with that build.
- A disc whose track file is missing is refused and disc 1 stays in, with the tray shut.
- One disc offers the controls with nothing to swap to, and its state has no section; a cartridge
  offers none; a playlist with no disc in it is refused in a sentence.
- The save cartridge is 128 KB and formatted; bytes the console writes to it over its own bus,
  and a byte written from the app's side, go to `<game>.bcr`; nothing is rewritten when nothing
  changed; and a fresh launch gets the cartridge back before its first frame.
- Always run (`bridge.rs`, with the test core): the `.bcr` file is written beside the `.srm`, only
  when it changed, comes back on the next launch, a file of another size is left alone, and no
  other core is asked for the cartridge.

### What was not proved, and needs a phone

- **A real disc swap.** Whether a real game, on a real Sega CD start-up ROM, notices the new disc
  and carries on. The drive goes through the states a real drive does, but no game was there to
  watch it. That needs a phone with a multi-disc game and the player's own start-up ROM.
- Whether a game or the console's memory screen reads and writes the cartridge as it should; only
  six instructions of our own wrote to it here.
- An old Genesis Plus GX save cartridge file is not picked up: its layout could not be checked
  here, and loading one wrongly would scramble it, so the cartridge simply starts empty.

## 4. 32X games without the 32X BIOS files: Continuum's own start-up code (Built, untested)

What a player gets:

- **A 32X game just starts.** Before, the app refused it with "32X games need two files from a
  real 32X: 32X_M_BIOS.bin and 32X_S_BIOS.bin". Those are the start-up programs of the 32X's two
  processors; Continuum now has its own, so a 32X cartridge needs no files at all.
- **A player who has the two files keeps using them**: when both are installed, BlastEm runs them,
  as before, and the install button still knows both names. Settings, BIOS has one line for the
  32X: "Sega 32X: works without a BIOS (looks for 32X_M_BIOS.bin and 32X_S_BIOS.bin)", or "using
  32X_M_BIOS.bin and 32X_S_BIOS.bin" when both are there. One file without the other is not used
  (the line says "works without"), because mixing one of theirs with one of ours was never tested.
- **Unchanged: a 32X CD** (the few Sega CD discs that also use a 32X) still needs the two files.
  The start-up code only knows cartridges; a disc reaches the 32X by another way, which this code
  does not do. Those discs open as Sega CD games, which they always did.

What was built:

- **A fourth BlastEm patch, `scripts/patches/blastem-32x-startup.patch`**, applied after the other
  three:
  - `continuum_32x_boot.s`, the start-up code, SH-2 assembly written for Continuum from Sega's
    published 32X hardware manual (section 5.1, "Boot ROM": the header a 32X cartridge carries at
    $3C0, the copy of the game's SH-2 program it describes, "M_OK" and "S_OK", the checksum in
    comm8) and from what the Mega Drive side's start-up program, which every 32X cartridge carries
    unchanged at $3F0, does and waits for. It is not Sega's code; GPL-3.0-or-later like BlastEm.
    The main processor waits for the adapter to be switched on, clears the 32X's memory, posts the
    header's checksum, copies the game's SH-2 program where the header says, waits for the Mega
    Drive side to finish with the 32X (below), posts "M_OK" and starts the game at its own entry,
    with its own vector table and stack. The second processor waits for "M_OK", posts "S_OK" and
    starts its half of the game. 1,208 and 1,136 bytes.
  - `continuum_32x_boot.h`, those bytes, assembled with GNU binutils 2.43.1 for sh-elf, built from
    source here (the commands are at the top of the `.s`), with each image's sha256.
  - `32x.c`: the player's own pair when both are usable, by the same rule BlastEm's load check
    uses (a reset vector that is not zero, so an empty placeholder counts as no file), and
    Continuum's pair otherwise; a 32X CD still gets only the files.
  - `libblastem.c`: BlastEm's refusal at load ("32X needs the Main and Sub SH2 BIOS ROMs ...") is
    left for a 32X CD only.
  - `sh2.cpu`, **a bug in BlastEm's SH-2 processor**: a reset kept an instruction the processor
    had read ahead before the reset, and ran it in place of the first instruction after it. The
    Mega Drive side resets the SH-2s while they wait for it, so the first instruction of the
    start-up code (the one that points at the 32X's registers) was skipped and the SH-2 never saw
    the adapter switched on. That is why the code drafted the night before did not start
    anything. Upstream BlastEm has the same bug (libretro/blastem's newest commit is still our pin,
    `ab74365`). With the console's own start-up files it only did no harm by luck of where their
    code sits at that moment; the fix makes a reset start exactly where the reset vector says, as
    the real chip does.
- **The wait for the Mega Drive side.** Measured in BlastEm: the Mega Drive side's start-up program
  starts the SH-2s, then spends about 22 ms clearing the 32X's registers, both picture buffers and
  the palette, and only after that reads the checksum and clears comm8 to comm14, its last touch
  of the 32X. HexGL copies only 16 bytes, so without a wait its SH-2 code was already running about
  2 ms before that clearing ended, while the Mega Drive side still owned the 32X's picture. (The
  console's own start-up program is slow enough, with its memory test and security check, that
  this never happens on a real 32X.) So the main processor leaves a mark in comm12 before it starts
  and posts "M_OK" only once the mark is gone; with it, HexGL's "M_OK" comes 63 master clocks
  after the Mega Drive side's last write. If the mark is never cleared (an SH-2 reset with no
  start-up program behind it) it gives up after 0.64 s, takes the mark out and starts the game
  anyway, so it can never freeze one; checked with a build that ignores the clear.
- **The app** (`ContinuumApp.swift`): the 32X left the launch check (`requiredFirmware`) for a new
  list, `optionalFirmware`, which gives Settings its line and the install button its two names. The
  32X's launch line, which nothing can reach now, is deleted rather than reworded.
- **`scripts/build-core.sh`**: the blastem arm applies the new patch after the other three, and
  the blastem comment says what it is. Both edits are inside the blastem regions, so they move
  BlastEm's fingerprint only.

### What the tests prove

`crates/emulator-bridge/tests/blastem_frontend.rs` (opt-in: `BLASTEM_SO`, and `BLASTEM_32X_DIR` for
the games): BlastEm built for the host from its pin with all four patches, loaded through the same
libretro entry points the app uses, with two openly licensed 32X games that the repository does
not ship: the 32X port of Artemio's 240p Test Suite (GPL-2.0, Dasutin/32X240pTestSuite, release
v1.0) and HexGL 32X (MIT, haroldo-ok/hexgl-32x, release v0.0.1). They are two authors' work, and
two different ways of starting: the 240p suite copies 126,704 bytes of SH-2 program and has no
checksum, HexGL copies 16 bytes, runs its SH-2 code straight from the cartridge and has one.

- **With no 32X files at all, both start**: each one's SH-2 program is in the 32X's memory where
  its header asks, and both draw a picture of many colours at 5 and at 10 seconds: the 240p
  suite's main menu (21 colours) and HexGL's title screen (60 and 61). Both frames were looked at.
- **The player's own files come first**: a pair of stand-in files that never hand over (their
  reset vector points at a jump to itself) leaves both games at one colour for ten seconds, which
  is also what shows the pictures above come from SH-2s Continuum's code really started. Empty
  placeholder files, and one stand-in file without the other (either one), start both games on
  Continuum's code.
- The earlier BlastEm tests still pass with the fourth patch: the cartridge list (section 2), and
  the Sega CD discs and save cartridge (`src/cores/blastem_host_tests.rs`, section 3).

`crates/emulator-bridge/tests/blastem_32x_boot.rs` (new): always, both images are in the header, fit
the 16 KB start-up window and start where an SH-2 coming out of reset looks; with `SH_ELF_BIN`
pointing at binutils for sh-elf, the `.s` in the patch, assembled with the commands at its top, is
byte for byte the header (one changed byte makes it fail; tried). `tests/blastem_rom_db.rs` with
`BLASTEM_SRC`: the four patches apply to the pinned source in the build's order, and applying them
by hand gives exactly the tree that was tested. The workspace: 736 tests pass, clippy is clean,
`scripts/check-core-cache.sh` 218 passed.

### What was not proved

- **Commercial 32X games.** None was used here: they are not ours to fetch. The code does what
  the manual says the console's start-up program does, plus the wait, but a game that leans on
  something else that program leaves behind (a register value, a timer setting) would not have
  shown up in two homebrew games. A player who has the two files is unaffected: they are used.
- The reset fix with the console's own files, which nobody here has. It can only make a reset
  start where the chip would, but that was not watched.
- Speed is not affected: the start-up code runs once, for well under a second.
- **Found while looking, not changed:** BlastEm's save states hold only the Mega Drive half of a
  32X game. Its state writer (`genesis_serialize`) has no section for the 32X, and nothing in its
  32X or SH-2 code writes one, so loading a 32X save state cannot put the 32X's two processors or
  its memory back. That was already so with or without the files; fixing it is a job inside
  BlastEm's state format (a new section and a version gate), not part of this item.

## 5. Mesen 2 as the second choice for SNES games (Built, untested)

What a player gets:

- **Settings, Cores has a "Core for SNES games" choice: bsnes or Mesen.** bsnes stays the default,
  so nothing changes for anyone who leaves it alone. A single game can be moved too, from its card
  ("Runs on"), the same way NES games choose between Mesen and FCEUmm.
- **On Mesen, an SNES game gets everything it gets on bsnes:** its in-game save is kept by the
  app (backed up and synced like every other save), RAM search and achievements see its memory,
  and typed Game Genie and Pro Action Replay codes work. The cheat screen's line names the SNES
  codes on an SNES game and the NES ones on an NES game.
- **The save is the same file on both emulators**, so switching keeps it: a game saved on bsnes
  carries on from that save on Mesen, and back.
- **The picture is the same as on bsnes:** the 224 lines a game draws, at 4:3, with no black bands
  inside it. Save states stay with the emulator that made them, as on the NES.
- If bsnes refuses a game, the app's existing one-retry now tries it on Mesen.

Why it was not offered on 13 October: everything the Mesen patch gave the NES was written for the
NES only (night batch report, A9). That is what this fixes.

What was built:

- **A second Mesen patch, `scripts/patches/mesen2-snes-memory-cheats-saves.patch`**, applied after
  the NES one (its context is the file as that one leaves it; `scripts/build-core.sh` applies both
  in order, inside Mesen 2's own regions):
  - **Memory.** `retro_get_memory_data` hands over the SNES's 128 KB of work RAM (`$7E0000-$7FFFFF`)
    as system RAM, and as save RAM the battery RAM Mesen itself would have kept as the game's
    `.srm`: the GSU's RAM for a battery SuperFX game, the ST010/ST011's for those two, the SA-1's
    own RAM for the one SA-1 game with no other save RAM, and the cartridge's RAM for everything
    else (`BaseCartridge::ContinuumBatteryRam`, the same choice Mesen's own save makes). That is the
    same region bsnes's patch hands over, so the file is one file. No memory map is published for
    the SNES, on purpose: RetroAchievements reads SNES cartridge RAM from save RAM, and through a
    map it would read nothing there (the engine's port of rcheevos says so, as RetroArch does), so
    achievements see exactly what they see on bsnes.
  - **Cheats.** `retro_cheat_set` reads SNES codes on an SNES game and hands them to Mesen's own
    cheat code: Game Genie as `XXXX-XXXX`, Pro Action Replay as `AAAAAAVV`, `AAAAAA:VV` or
    `AAAAAA=VV` (the spellings bsnes takes), parts joined with `+`. One part that is not a code
    makes the whole code do nothing, as on the NES. NES games read NES codes exactly as before.
  - **The battery save belongs to the app.** Mesen no longer reads or writes a `.srm` of its own
    for the cartridge, the GSU, the SA-1 or the ST010/ST011 (each place it did was gated, the same
    flag the NES patch added). Before this, Mesen would have written `<game>.srm` straight into the
    app's support folder, outside the save system: checked with the NES-only build, which wrote
    one; this build writes none. Clocks (SPC7110), Satellaview memory packs and the like keep their
    own files, as they do on bsnes.
  - **The picture.** SNES frames go out without Mesen's 7 and 8 blank lines (256x224), and the core
    reports 4:3, both as bsnes in the app does. The app gives an SNES game on Mesen bsnes's 4:3
    shape too (Mesen's spec carries the NES's shape).
- **The engine:** `cheats::formats::code_support_on` (and `cheat_code_support_on` for the app) names
  the codes per system; the zero-padding a `.srm` from another SNES emulator can carry is trimmed
  for an SNES game on Mesen as it already was on bsnes (`battery_layout::fit_padded` now takes the
  file's extension; an NES game on Mesen is unchanged); the update heads-up calls Mesen "the NES and
  SNES emulator". Mesen 2's pin does not move, so no heads-up shows for this.
- **The app:** Mesen's spec lists `snes` and the SNES hi-res size, the SNES choice list is bsnes
  then Mesen, the credits say "NES, SNES", and the "now launch on" line says "Mesen", not the
  spec's full name.
- **The build cache:** only Mesen 2's fingerprint moves (`4e26c0d8`, was `daffa958`); bsnes,
  FCEUmm, BlastEm, Gearsystem and cArcade are unchanged, checked before and after on today's
  master. `scripts/check-core-cache.sh`: 219 passed.

### What the tests prove

`crates/emulator-bridge/src/cores/snes_host_tests.rs` (opt-in: `MESEN2_SO`, `BSNES_SO`,
`SNES_HOMEBREW_DIR`; the file's top says how to build both cores). Mesen 2 built for the host
from its pin with both patches, with the iPhone build's flags (`-O3`, no LTO), and bsnes from its
pin with its patch, each inside a real engine session, launched the way the app launches a core.
The build script's own patch step was run on a clean checkout and gave exactly the tree that was
tested. The games, fetched into scratch and not committed: Artemio's **240p Test Suite** (GPL-2.0),
**MicroPython for SNES**'s workstation (MIT, FabianKuebler/micropython-snes; it keeps its files in
32 KB of battery RAM) and **Gothicvania** (MIT, donth77/snes-homebrew), plus a 128 KB test
cartridge of our own the tests build (8 KB of battery RAM with a boot counter in it, a ROM byte
and a work RAM byte it keeps copying, a frame counter).

- **The games run:** all three draw their screens at 256x224, the 240p menu's highlight moves
  when Down is pressed, and the frames were looked at.
- **Battery save round trip:** our cartridge's boot counter goes up by one on every start, from
  the save the app put back before the first frame (three starts in a row); nothing is rewritten
  when nothing changed; and no `.srm` of Mesen's own appears, even after the game closes. The
  MicroPython workstation formats its battery RAM on a first start; with the app's save put back
  (its file renamed in the save, from hello.py to keep.py) it lists keep.py and does not format
  again; bsnes, given the same file, finds keep.py too.
- **The save moves between the two emulators:** Mesen, bsnes, Mesen, bsnes, each counting on from
  the other's save.
- **Save state round trip:** on all four games a state comes back exactly (all 128 KB of work RAM
  matches, and 120 frames later it matches what the game did the first time), and the same state
  loads into a fresh start of the game.
- **Cheats change memory:** a Game Genie code on a ROM byte changes what the game copies (to `$77`)
  and switching it off puts the ROM's own byte back; Pro Action Replay codes on a ROM byte and on
  a work RAM byte work in all three spellings, two codes joined with `+`; a code with one bad part
  does nothing. The same codes do the same on bsnes. RAM search finds the frame counter alone in
  five steps and pinning it holds it, and achievements' view of memory reads work RAM at `$000000`
  and the cartridge's RAM at `$020000`.
- **The NES is as it was:** an NES cartridge of our own on the same build still gets its 2 KB RAM
  and 8 KB save, its save comes back, raw NES codes work, an SNES-shaped code does nothing, and no
  `.sav` of Mesen's own appears. The NES-only build fails every SNES test (no memory, so no save,
  no cheats, no RAM search), so they test what changed.
- The workspace: 749 tests pass (the opt-in ones say they were skipped), clippy is clean, the
  Swift files parse, and the regenerated bindings type-check with the new call as the app writes it.

**Speed**, frames per second on this Linux machine (x86-64, one thread, shared with other jobs, so
the numbers move by about 10% between runs), 1800 frames after four seconds of warm-up, as the
engine runs them with no picture drawn. "bsnes" is bsnes with the settings the app gives it (its
fast PPU, DSP and coprocessor paths); "bsnes accurate" has those three off, which is closer to what
Mesen always does.

| Game | Mesen 2 | bsnes | bsnes accurate |
| --- | --- | --- | --- |
| Our test cartridge | 491 (8.2x full speed) | 732 (12.2x) | 145 (2.4x) |
| 240p Test Suite | 319 (5.3x) | 462 (7.7x) | 151 (2.5x) |
| Gothicvania | 332 (5.5x) | 511 (8.5x) | 149 (2.5x) |
| MicroPython workstation | 357 (5.9x) | 583 (9.7x) | 156 (2.6x) |

So Mesen runs at about 60 to 70% of bsnes's speed as the app sets bsnes up, and two to three times
bsnes's accurate mode. On a phone it needs about one and a half times the processor bsnes does.
Save states: Mesen's are about 0.55 MB against bsnes's 0.28 MB (Mesen asks for twice the room its
state uses), so rewind, which keeps a fixed amount of memory, holds about half as many seconds.

### What was not proved, and needs a phone

- **Speed on an iPhone**, and whether demanding games (SuperFX, SA-1) keep full speed on Mesen. No
  homebrew here uses those chips.
- The GSU, SA-1 and ST010/ST011 save paths were changed by reading Mesen's code, not run: no
  open-licensed game here has those chips.
- Commercial games: none was run. Their cheat codes were not tried either; the codes above are our
  own, encoded the way both emulators decode them.

### Known differences, not fixed

- **Chip files.** Mesen has no stand-in versions of the DSP chips, and it picks the file by game:
  Pilotwings wants `dsp1.rom`, the other DSP-1 games `dsp1b.rom`. The app's launch check accepts
  either name (bsnes is fine with either). So a player with only one of the two files should keep
  those games on bsnes; on Mesen the chip would be missing and the game would misbehave rather than
  say so. Not changed: the fix (trying the other file) could not be checked without the files.
- **Two pads only** on Mesen's SNES: its libretro side offers no multitap and no SNES mouse, so the
  controller choice shows only what Mesen offers. Games for more than two players stay on bsnes.
- **Found while looking, in bsnes, not changed** (its patch is not this job's): bsnes writes a ROM
  code into the ROM and, when it is given two codes at once, forgets the original byte of every
  part but the last, so switching off a `+`-joined code leaves its first part in until the game is
  opened again. Mesen does not have this (it changes what the game reads, not the ROM).
