# Folder-scoped picker for multi-file cue/bin PS1 ROMs (v1)

The iOS ROM flow moves from a single-file `.fileImporter` to a folder picker so PCSX ReARMed can read the `.bin` tracks a `.cue` references. Picking a single `.cue` scoped only that one file, so the C++ core's `fopen` of adjacent `.bin` tracks landed outside any granted security scope and iOS denied it; cue/bin games failed on device. The fix scopes the whole picked folder for the session, enumerates it to choose a launch entry by extension priority (`.cue` > `.pbp` > `.iso` > `.chd` > `.bin`), and hands that entry's absolute path to the unchanged Rust `need_fullpath` launch. As a complementary path it enables `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace`, injected through `project.yml` `info.properties` because XcodeGen regenerates and overwrites the Info.plist.

Watch for: the folder scope is balanced across all four exit paths and re-entrancy (confirmed); the `.bin` last-resort can pick the wrong track for a multi-bin-no-cue folder (possible); on-device folder-scope and cue/bin boot are unverifiable in this sandbox (confirmed, out of scope for the diff).

**Verdict**: APPROVED

## High-level view

The core design change is that the security scope now attaches to the folder rather than the picked file. iOS grants a scope over the whole subtree of a picked folder, so the core can open the `.cue` and every `.bin` it names. The scope is taken once per successful pick, stored in `activeScopedURL`, and released in exactly one of four mutually exclusive places: `stopSession`, the no-entry path, the launch-failure path, or the start-access failure early return. That balance is the load-bearing property of the change.

Entry selection is deterministic. The folder is enumerated non-recursively with hidden files skipped, extensions are matched case-insensitively against a fixed priority list, and ties within the winning extension break on sorted `lastPathComponent`. A folder with no loadable descriptor fails legibly on the HUD and releases the scope without launching. The one soft spot is the `.bin` fallback, which has no way to know which raw track is the boot track when there is no `.cue`.

The API surface toward the user is a folder picker (`allowedContentTypes: [.folder]`, single selection) and relabeled buttons ("Open ROM Folder..."). The plist gains two file-sharing keys. The Rust launch contract is untouched: it still receives an absolute path with a real extension.

The Info.plist change is really a project.yml change. XcodeGen generates the plist from auto-defaults merged with `info.properties` and overwrites the on-disk file, so every custom key the app needs, not just the two new ones, must live in `info.properties`. The commit moves the full set there and keeps the committed plist as a matching seed.

### Folder scope replaces file scope, and its balance across exit paths

The whole fix rests on one behavioral shift: `startAccessingSecurityScopedResource()` is now called on the picked folder, and iOS extends that grant over the subtree, so the core opening a `.cue` and then its sibling `.bin` tracks all fall inside one scope. `activeScopedURL` holds the folder URL for the session lifetime; it is deliberately not released in a `defer` right after launch because `need_fullpath` keeps the files open for the whole run.

`launch(url:)` opens the scope exactly once per successful pick and releases it in one of four mutually exclusive places:

```
launch(url:)
  running || activeScopedURL != nil -> stopSession()   // releases any prior scope first
  startAccessingSecurityScopedResource() == false -> return   // nothing taken, nothing to release
  activeScopedURL = url                                 // the one start
  selectLaunchEntry == nil -> stop + nil + return       // release (no-entry)
  engine.launch throws       -> stop + nil + return     // release (failure)
  engine.launch succeeds     -> held until stopSession() // release (session end/replace)
```

Re-entrancy is safe: a fresh pick runs `stopSession()` first, which releases the previous folder's scope and clears `activeScopedURL`, so there is never a second live start against a stale URL and no leak when the user opens another folder mid-session. The start-access failure return happens before `activeScopedURL` is assigned, so there is no phantom release of a scope that was never taken. All paths are balanced (confirmed).

### Deterministic launch-entry selection, and the .bin blind spot

`selectLaunchEntry(in:)` enumerates the folder non-recursively with `.skipsHiddenFiles`, then walks the fixed priority list `["cue","pbp","iso","chd","bin"]`, filtering by lowercased `pathExtension` and sorting matches by `lastPathComponent` before taking the first. Case-insensitive matching and the sorted tie-break make the choice stable across enumeration order, which matters because `contentsOfDirectory` order is not guaranteed. A `.cue` that references its `.bin` tracks is now openable because the folder, not the cue alone, is scoped (confirmed). The non-recursive enumeration means a `.cue` nested one directory below the picked folder is not found, which is consistent with the "pick the folder that directly holds the files" affordance.

The `.bin` entry sits last precisely because it is a raw single-track image with no descriptor. When a folder contains multiple `.bin` files and no `.cue`, selection takes the alphabetically first `.bin`, which is not necessarily the boot track (possible). This is a genuine last resort and the priority list correctly prefers any descriptor over it, so a normal cue/bin layout never reaches this branch. Still, for a multi-bin-no-cue folder the pick is a guess; a short HUD note that a descriptor is missing, or declining to launch, would be more honest than silently booting a possibly-wrong track. Not blocking.

The no-entry path fails legibly: the HUD shows `no .cue/.pbp/.iso/.chd found in <folder>`, the scope is released, and no launch occurs (confirmed).

### Info.plist keys ride on project.yml info.properties

The two new keys, `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace`, are added to `info.properties` in `project.yml`, not merely to the committed `Info.plist`. This is the correct lever: XcodeGen emits the plist from its auto-default keys merged with `info.properties` and overwrites `info.path` when they differ, so anything only in the committed file would be dropped from the built app. The commit moves the full custom set into `info.properties` alongside the two new keys.

Cross-checking `info.properties` against the seed plist, every previously-shipping custom key is carried: `CFBundleDisplayName`, `CFBundleShortVersionString` restated as `0.8.0` (overriding the XcodeGen `1.0` default), `CFBundleVersion` `1`, `LSRequiresIPhoneOS`, `MinimumOSVersion` `16.0`, `UIRequiredDeviceCapabilities` `[arm64, metal]`, `UILaunchScreen` as an empty dict (`{}`), `UIApplicationSupportsIndirectInputEvents`, `UIStatusBarHidden`, `UIViewControllerBasedStatusBarAppearance` `false`, and both orientation arrays including the `~ipad` variant. Booleans are YAML `true`/`false`, versions are quoted strings, and `UILaunchScreen: {}` maps to the plist empty `<dict/>`. Nothing is silently dropped and the version override that XcodeGen would otherwise clobber is preserved (confirmed).

Files dragged into Documents via the file-sharing keys live inside the app sandbox and need no security scope, so that path does not exercise the folder-scope machinery at all.

### HUD and Rust contract

The status strings and button labels track the folder model: "surface ready - pick a PS1 ROM folder", "Open ROM Folder...", "running: <entry> (folder: <folder>)", and "no folder selected" on an empty pick. The Rust launch call is unchanged in shape; it still receives `rom: Data()` and an absolute `filename` with a real extension (now the selected entry's `.path` rather than the raw picked URL's), which is exactly what the `need_fullpath` routing expects. No Rust, build-script, or workflow files are touched by this commit, matching the constraint that the launch path stays as-is.

Not tested: none of this is exercisable in the sandbox. There is no macOS, Xcode, iOS SDK, or xcodegen, and `swiftc -frontend -parse` is a spell-check that cannot validate the `.fileImporter([.folder])` call, the `FileManager` enumeration, or the scope balance. On-device folder-scope grant and cue/bin boot are verifiable only by the orchestrator's CI build and a device run afterward; their absence here is not a defect.
