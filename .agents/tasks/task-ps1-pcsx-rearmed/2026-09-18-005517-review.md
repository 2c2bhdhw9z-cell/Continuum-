# First real libretro core: PCSX ReARMed (PS1) through the software frame path (v1)

This change swaps the Switch stub for the first real libretro core, PCSX ReARMed, loaded through the existing native software frame path as a thin `dlopen` passthrough. The bulk of the work is in `on_environment`, which grew from the ~6 commands the stub needed to the full set a real PS1 boot exercises inside `retro_load_game`: `SET_PIXEL_FORMAT` negotiation, `GET_VARIABLE` answered as "use your default", and a family of option/descriptor/message commands accepted as no-ops. Supporting it are a negotiated-pixel-format global so `video()` reports the core-chosen format instead of a hardcoded `Rgba8888`, a `ContentHint::full_path` so a `need_fullpath` core receives a real openable path, and a build-pipeline chain (`build-core.sh` → `build-engine.sh` → `project.yml` → `package-ipa.sh` → `ios.yml`) that compiles the core from source on macOS CI and embeds the `.dylib`. Bundled alongside is an unrelated `[profile.ios]` (`panic = "unwind"`) so panics reach the HUD rather than aborting.

Watch for: the `panic = "unwind"` Cargo profile is a separable concern riding in the same branch (confirmed); the PS1 boot path cannot be executed anywhere in this environment and is verified only by CI producing a signed bundle (confirmed, documented); `full_path` is silently dropped for bare filenames, so a `need_fullpath` core given a name-only hint falls back to the stem and would be rejected by the core (likely).

**Verdict**: APPROVED

## High-level view

The loader stays a thin passthrough: `native_core.rs` `dlopen`s the core and forwards `retro_*` directly, with no switch-wrapper FrameGate on the path. The stub harness remains a live, independent gate reserved for the future standalone Switch engine.

The environment handler is the heart of the change. Every command number is machine-checked against the vendored `libretro.h` with an inline citation, and the design leans on libretro's contract that `false` means "unsupported": unlisted commands fall through to a silent default-false arm. Two commands are refused on purpose — `SET_AUDIO_BUFFER_STATUS_CALLBACK` (to avoid promising a callback that is never made) and `GET_INPUT_BITMASKS` (to route the core onto the per-id `input_state` path that `InputSnapshot` already serves).

Pixel-format negotiation replaces a hardcoded `Rgba8888` in `video()` with the format the core actually chose. The value travels through a process-global `Mutex<Option<PixelFormat>>` (same lifetime rationale as `DIRECTORIES`), is reset before each load, and defaults to the descriptor's declared format when no `SET_PIXEL_FORMAT` arrives. The switch-stub path is unaffected because its descriptor already declares `Rgba8888` and it never negotiates.

The `need_fullpath` plumbing adds an optional `full_path` to `ContentHint`, populated by `from_filename` only when the input contains a directory separator, and consumed by `load_content` only when the content bytes are empty. The web/in-memory path and the switch-stub path see identical behavior.

The build chain pins one filename — `pcsx_rearmed_libretro_ios.dylib` — across five files, defined once in `build-core.sh`. The iOS core path is Darwin-guarded and dispatched before the wasi-sdk machinery, so the web build is untouched. The Swift host, the handoff doc §17, and the Rust behavior agree on the negotiation, the BIOS/HLE fallback, and the fullpath requirement.

Test coverage is solid for the environment handler and the hint parsing; the pixel-format negotiation lifecycle end to end (load → negotiate → `video()` reports it) and the `load_content` full_path selection are not directly tested.

### Environment protocol: what a PS1 boot needs, and what is refused on purpose

Every command number carries a `libretro.h:line` citation. `SET_PIXEL_FORMAT` reads a `*const c_uint` after a null check and maps it through `PixelFormat::from_libretro` (libretro numbering 1=XRGB8888, 2=RGB565, 0=0RGB1555 rejected); a rejected format returns `false` and stores nothing, matching PCSX ReARMed's behavior of keeping its current format rather than aborting.

`GET_VARIABLE` is the one that most easily goes wrong. The pointer arithmetic — `(data as *mut *const c_char).add(1)` to reach `value` past `key` — is correct for the two-pointer `retro_variable` layout, and it null-checks `data` first before nulling the `value` slot and returning `false` ("unset, use your default"). Fabricating option strings is how a core ends up configured in a way nobody chose, so declining to is the right call.

`SET_AUDIO_BUFFER_STATUS_CALLBACK` (62) is refused because accepting it would promise a callback the host never makes; `GET_INPUT_BITMASKS` (51|EXPERIMENTAL) is refused so the core falls back to per-id `input_state`, which `InputSnapshot::libretro_state` already serves. Both are covered by tests asserting `false`. `GET_CORE_OPTIONS_VERSION` reports 0, which is internally consistent: the `SET_CORE_OPTIONS*` families are accepted as no-ops but none of their query surface is implemented, so 0 keeps the core on the `SET_VARIABLES`-era path rather than claiming a v1/v2 option API that would then be queried.

### Pixel-format negotiation and the reset lifecycle

```
retro_load_game()  ── SET_PIXEL_FORMAT ─▶ store_negotiated_format() ─▶ NEGOTIATED_FORMAT (global)
       │                                                                      │
load_content:  reset_negotiated_format()  ── before load ──┘                  │
               take_negotiated_format()    ── after load ───────────────────▶ self.negotiated_format
                                                                              │
video()  ── format: self.negotiated_format ───────────────────────────────────┘
```

The global is reset before each `load_game` so a stale format from a prior core cannot leak, then read back into the per-instance `negotiated_format`, which seeds from the descriptor's declared format. Because the software path stores raw core bytes with the reported pitch, reporting the true format is what lets `gfx/convert.rs` normalize RGB565 vs XRGB8888 correctly — the previous hardcoded `Rgba8888` would have mis-decoded any real core that emits RGB565.

One asymmetry to keep in view: `NEGOTIATED_FORMAT` is a single process-global, so two `NativeLibretroCore` instances loading concurrently would race on it — the reset-then-load-then-take sequence is not atomic across the load. In the current single-session iOS host this cannot happen, and the design mirrors `DIRECTORIES`, but it is a latent constraint rather than a guarantee.

### need_fullpath and the full_path plumbing

The selection in `load_content` is `match (content.is_empty(), hint.full_path.as_ref())`: only the `(true, Some)` arm uses the full path; everything else falls back to `name`. The gap: a caller that hands a `need_fullpath` core a bare filename (no `/`) gets `full_path == None`, falls back to the stem, and the core rejects the load with a generic `InvalidContent`. Every current caller passes an absolute path, so this is latent, but it trades a clear "you must pass a path" signal for a downstream core rejection.

### Build pipeline: one filename across five files

`build-core.sh` gains a Darwin-only `build_ps1_ios_core` that clones `libretro/pcsx_rearmed`, inits submodules, runs `make -f Makefile.libretro platform=ios-arm64 IOSSDK=<sdk>`, reasserts the `@rpath/pcsx_rearmed_libretro_ios.dylib` install name via `install_name_tool`, and stages into `native/ios/build/lib`. It is dispatched before `ensure_toolchain`, so the wasi-sdk web path never runs and `web/cores/` is never touched — the "web build untouched" claim holds. The `DYNAREC=0` interpreter-only build is the Makefile's choice for iOS arm64, documented as a deliberate first-build tradeoff, not a defect.

The filename `pcsx_rearmed_libretro_ios.dylib` is defined once (`PS1_DYLIB_NAME`) and referenced identically by `build-engine.sh` (stage + hard-fail-if-missing), `project.yml` (`embed:true, link:false, codeSign:false`), `package-ipa.sh` (fallback copy), and `ios.yml` (unzip grep). I verified all five references match byte-for-byte, which is what keeps macOS CI green. `embed:true, link:false` with a signing pass in `package-ipa.sh` mirrors the existing switch-wrapper handling, so a wrong rpath surfaces as a legible HUD line rather than a launch failure.

The `[profile.ios]` addition (`inherits = "release"`, `panic = "unwind"`) is the one change not about the PS1 core. It is correct and well-reasoned — release stays `panic = "abort"` so `wasm32-unknown-unknown` (no unwinder) and `cargo test` are untouched, and `build-engine.sh` correctly moves its artefact reads from `target/$TARGET/release` to `target/$TARGET/ios`. The host-side uniffi-bindgen still builds under `target/release`, which is correct because the metadata is profile-independent. The concern is scope, not correctness: it is a separable change bundled into the PS1 branch.

### Swift host and handoff doc consistency

One cross-reference worth confirming because two pixel-format numberings coexist in this codebase: Swift's `pixelFormat: 0` uses the bridge's own `from_u32` numbering (0 = `Rgb565`), not libretro's (where 0 = 0RGB1555). `uniffi_api.rs` converts declarations through `from_u32`, so the declaration correctly means RGB565, and it is superseded by `SET_PIXEL_FORMAT` negotiation regardless. The Swift passes an absolute `filename` with empty rom bytes (so `full_path` is populated) and surfaces BIOS/HLE state on the HUD, and doc §17 matches the Rust behavior including the negotiation, the two deliberate refusals, and the fullpath requirement.

### Test coverage

The environment handler is well covered: RGB565/XRGB8888 stored, 0RGB1555 refused with nothing stored, `GET_VARIABLE` nulls a seeded non-null `value` and returns false, the no-op families all return true, `SET_AUDIO_BUFFER_STATUS_CALLBACK` and `GET_INPUT_BITMASKS` refused, `GET_CORE_OPTIONS_VERSION` reports 0, and `from_filename` records `full_path` only for paths. A dedicated poison-tolerant lock serializes the format tests against the process-global. The 84-test `--features native-core` run passes.

Not tested: the negotiation lifecycle end to end (load → `SET_PIXEL_FORMAT` → `video()` reports the negotiated format), and the `load_content` full_path-vs-name selection. Both are only reachable through a loaded core, which needs a fake libretro `.dylib` fixture; the handler-level unit tests cover the store/take halves but not the seam that wires them into a frame.
