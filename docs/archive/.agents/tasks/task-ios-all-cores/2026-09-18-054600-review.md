# All five libretro cores in the iOS .ipa (v1)

The .ipa went from shipping one core to shipping every core the web PWA has plus PS1. `scripts/build-core.sh` grows an `ios` / `ios-all` / `ios-names` subcommand namespace so a bare core name keeps meaning "build as WASM for the web", four of the five cores build through their upstream `platform=ios-arm64` makefile target and mgba (which ships no makefile) is configured with CMake and linked into a dylib by hand, the artefact chain stages and asserts all five, and `ContinuumApp.swift` replaces the hardcoded PS1 declaration with a five-entry `CoreCatalog` plus one extension-to-core routing table that both the Library row and the launch path read. All five cores are declared when the surface attaches and exactly one is loaded, on demand, from the tapped file's extension. No Rust changed.

Watch for: the macOS job's `timeout-minutes: 60` was not raised even though the build step now compiles five native cores instead of one, with no source caching (confirmed budget, likely timeout); `ios-all` runs each core in an `if`-condition subshell, which suppresses `set -e` for everything inside it, so a failed `make` is not itself an error and a leftover dylib in the never-cleaned `.work/ios` tree can be staged and reported `ok` (confirmed); nothing anywhere verifies a staged dylib exports the libretro entry points, which is the specific failure mgba's hand-rolled `-force_load` link over an LTO archive can produce (confirmed absence); the BIOS HUD line no longer appears at attach and its doc comment still says it does (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The namespace decision is the load-bearing design call. A bare core name is live in `deploy.yml`, `core-abi-test.mjs` and `web/cores/README.md`, so the iOS builds got their own subcommands rather than overloading `fceumm`; the dispatch `case` at line 858 exits before `ensure_toolchain` at 883, the old `PS1_*` globals are gone with no dangling references to trip `set -u`, and nothing under `web/` is touched. iOS sources also clone into `.work/ios/<core>` rather than sharing `.work/<core>` with the WASM path, which matters because both builds compile in tree and would otherwise link each other's objects.

Five dylib filenames are the change's failure surface, and they are handled asymmetrically: `build-engine.sh` and `package-ipa.sh` read them from `ios-names` and cannot drift, while `project.yml`, `ios.yml` and `CoreCatalog` restate them by hand. `ios-names` runs on any host, which makes that agreement scriptable from Linux, but no script checks it.

`ios-all` deliberately continues past a failed core so one macOS cycle reports on all five. The mechanism defeats the strictness the rest of the script relies on: inside an `if`-condition subshell bash ignores `set -e`, so only the artefact-existence checks decide pass or fail, and `build_ios_make_core`'s fallback `find *.dylib` stages whatever it finds under the canonical name. The same failure is hard through `ios <core>` and soft through `ios-all`.

mgba is the one core whose link this project owns, and the upstream reading behind it holds up against `libretro/mgba` master. What is unguarded is the outcome: `-force_load` over an archive of LTO bitcode is the one place a valid, empty dylib is plausible, and every downstream check only asks whether a file exists.

CI got five greps with distinct `::error::` messages and no restructuring, as asked, but its time budget did not move. One 60-minute `macos-latest` job now clones five repositories (one full-depth with recursive submodules), runs four makefile builds and a CMake build with `-flto`, and still has to fit xcodegen, xcodebuild, signing and packaging in the same hour. Nothing caches `.work/ios`.

The Swift side meets every pinned requirement: the five specs carry the exact geometry, fps, sample-rate, pixel-format and priority values, `ensureCoreLoaded(coreId:)` re-reads `engine.coreState` on entry and again after declare-plus-load with no Bool anywhere, and the routing table has one copy that both the row detail and `launch(entry:)` consult. The regression is in the HUD: `bios` used to be written at attach through the old unconditional `ensureCoreLoaded()`, and the replacement `declareAllCores()` never touches it, so the BIOS/HLE readout now appears only after a PS1 game is tapped.

### Five filenames as a cross-file contract

The list is defined once in `ios_core_config()`, but only two of its five consumers read it:

```
scripts/build-core.sh  ios_core_config()          <- the only definition
        |
        |-- ios-names --> native/ios/build-engine.sh   asserts count == 5, stages, hard-fails by name
        |            \--> native/ios/package-ipa.sh    embed fallback + the unchanged codesign loop
        |
        \-- restated by hand in:
              native/ios/project.yml         5x embed:true link:false codeSign:false
              .github/workflows/ios.yml       5x unzip -l | grep -q, one ::error:: each
              native/ios/ContinuumApp.swift   CoreCatalog[].library
```

The three hand-copied sites agree today: `project.yml` parses with five `build/lib/*_libretro_ios.dylib` entries all carrying `embed: true`, `link: false`, `codeSign: false`, with `sources` and the fourteen-key `info.properties` block intact; `ios.yml` greps all five; `CoreCatalog` declares all five. So this is a missing guard rather than a present bug, and `ios-names` being host-independent is what makes the guard cheap to add.

`package-ipa.sh` now hard-fails when a staged dylib is absent, before it looks at whether the bundle already has it, with an error naming `build-engine.sh` as the fix. The `codesign --force --sign - --timestamp=none` loop over `Frameworks/*.dylib` and the single `--entitlements` sign of the bundle are untouched, so the JIT and increased-memory entitlements TrollStore depends on are unaffected and the four new dylibs are sealed by the existing glob.

### ios-all swallows build failures, and the dylib search can stage the wrong file

`build_all_ios_cores` runs each core as `if ( build_ios_core "$core" ); then`. Bash ignores `set -e` for a command used as an `if` condition, and that suppression is inherited by everything inside the subshell, including nested subshells:

```
set -euo pipefail
inner() { ( cd /tmp && false ); echo "REACHED"; return 0; }
if ( inner ); then echo "A: ok"; else echo "A: failed"; fi
# -> REACHED
# -> A: ok
```

Adding `set -e` inside the subshell does not restore it. So in `build_ios_make_core` a failing `make` does not abort the function; execution falls through to the dylib check, which is the only thing that decides pass or fail.

The two entry points therefore disagree. `build-core.sh ios fceumm` calls `build_ios_core` as a plain command with errexit armed, so a broken `make` aborts immediately. `ios-all` continues past it.

And the pass/fail decision now rests entirely on a file existing, while `.work/ios/<core>` is persistent: `ios_clone` skips cloning whenever `.git` is present, and nothing deletes the expected dylib before the build. A dylib left over from an earlier successful run satisfies the check after a failed compile, gets `install_name_tool`'d, copied, and printed as `==> <core> ok`. The fallback widens the target:

```bash
local built="$make_dir/$IOS_DYLIB_NAME"
if [[ ! -f "$built" ]]; then
  built="$(find "$make_dir" -maxdepth 1 -name '*.dylib' -type f | head -1 || true)"
fi
```

Any `.dylib` in the make directory gets renamed to the canonical name. The comment frames this as "better to stage a differently named dylib than to fail a build that succeeded", but all four makefile cores emit `$(TARGET_NAME)_libretro_ios.dylib` for an iOS platform, so the branch is reachable only when something is already wrong. `build_ios_cmake_core` takes the opposite line in the same situation: it prints the `.a` files it found and exits. That asymmetry is worth resolving toward the cmake path.

A clean CI checkout has no leftover artefacts, so today this is a local-iteration hazard. Adding the `.work/ios` cache from issue 2 brings it to CI, and `install_name_tool` or `cp` failing is silent through `ios-all` either way. `build-engine.sh`'s MISSING loop and the `ios.yml` greps remain the backstop for a dylib that never appears at all.

### mgba: the one link this project owns

The upstream reading checks out against `libretro/mgba` master: `-framework Foundation` and `-lm` are what mgba appends to `OS_LIB` on Apple, `LIBRETRO_STATIC=ON` takes the `STATIC` branch and so avoids the `--version-script` Apple's linker would reject, and `PREFIX ""` with a never-set `LIBRETRO_SUFFIX` yields exactly `mgba_libretro.a` in the build root. Two upstream behaviours the script calls out are real: `-flto` is appended to `CMAKE_C_FLAGS_RELEASE` for every Apple build, and `CMAKE_OSX_DEPLOYMENT_TARGET` is reset to `10.6` inside `if(APPLE)`, so the core objects compile at `-miphoneos-version-min=10.6` while the dylib links at 16.0 — a linker warning at worst.

What is missing is verification of the result. `-force_load` over an archive whose members are LTO bitcode is precisely the case where the link succeeds and produces a dylib with no libretro API in it, which is what the script's own comment gives as the reason the flag is there. Nothing downstream would notice: `build-engine.sh` checks the file exists and prints its size, `ios.yml` greps the zip listing for the filename, and `declareAllCores` checks the path exists in `Frameworks/`. The failure is at least legible when it lands, because `native_core.rs` resolves every entry point at load time and reports `missing symbol 'retro_init'`, which `ensureCoreLoaded` now surfaces as `mgba failed to load: ...`. But on a project with no device CI that costs a full build-plus-sideload cycle to learn, and an `nm -gU` assertion in `ios_stage_dylib` would cover all five for free.

The configure step carries the other mgba risk. `CMAKE_SYSTEM_NAME=iOS` puts CMake in cross-compiling mode, and mgba's configure performs the standard compiler check plus `check_symbol_exists(PATH_MAX "limits.h" ...)`, both `try_compile`s that build an executable. The script's comment identifies `-DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY` as the remedy and does not pass it. mgba is second in `IOS_CORES`, so under `ios-all` a configure failure still leaves the other four built and reported. What to check in the first CI log: whether the cmake configure reaches "Configuring done" or dies in the compiler check.

### One macOS job, 60 minutes, five cores from scratch

`ios.yml` is a single `macos-latest` job with `timeout-minutes: 60` and one cache, for `~/.cargo` and `target`. The "Build the engine, the wrapper and the UniFFI bindings" step now runs `ios-names`, then `ios-all`: five `git clone`s, of which `pcsx_rearmed` is deliberately full-depth with `git submodule update --init --recursive` for lightrec and libchdr; four makefile builds including snes9x's C++ tree; and mgba's CMake configure, `-flto` compile and whole-archive LTO link. Everything after that, from xcodegen through xcodebuild, ad-hoc signing, zipping, the nine `unzip -l` assertions and two artefact uploads, still has to fit in the same hour.

The failure mode is what makes this worth blocking on rather than watching. A timeout terminates the job with no `::error::` annotation and no artefact, at whatever step it happened to be in, which on a project whose only build machine is this runner reads the same as an infrastructure hang. Raising `timeout-minutes` costs nothing since the job is billed by the minute either way, and caching `.work/ios` on the hash of `build-core.sh` turns every subsequent run into a link rather than five builds.

### CoreCatalog and the single routing table

Every pinned value is present: fceumm `["nes"]` 256x240 at 60.0988 with 48000 Hz, snes9x `["snes"]` 256x224 at 60.0988 with 32040 Hz, mgba `["gba","gb","gbc"]` 240x160 at 59.7275 with 65536 Hz, genesis_plus_gx `["genesis","sms","gg"]` 320x224 at 59.9227 with 44100 Hz and a 348x240 max that clears the required 320x240, all `pixelFormat: 0` and `priority: 100`, and pcsx_rearmed unchanged at 320x240 / 700x576 / 59.94 / 44100 / priority 0 with its six BIOS filenames.

Routing has one copy and both consumers read it:

```
LibraryEntry.ext (already lowercased at construction)
        |
        v
CoreCatalog.routes  ---> CoreSpec
        |                    |
   row detail line      launch(entry:)
   "NES · 40 KB ·       -> status names spec.coreId
    fceumm"             -> ensureCoreLoaded(coreId:)
                        -> engine.launch(coreId:, filename: entry.path)
```

The route is resolved before the re-entrancy `stopSession()` so an unmapped extension cannot tear down a running game just to report itself. `launchableExtensions` is derived from `importableExtensions` by removing `bin` rather than restated, `routes` has a key for all fourteen derived entries, and the fifteen importable extensions are the required set exactly.

The invariants survive intact, checked individually: no Bool anywhere caches core residency; `engine.coreState(coreId:)` is read on entry, collapsed to `"unknown"` when nil so an undeclared id takes the reload path, and re-read after declare-plus-load; every early return writes a distinct status naming the core, with the unknown-id case separated from the missing-dylib case; the `ORDER IS LOAD-BEARING` comment and the after-`stopSession()` call site are unchanged; the launch path has no security-scoped URL (the file's one `startAccessingSecurityScopedResource` is the untouched defensive pair in `importFiles`); import still preserves original filenames and replaces on collision via `removeItem` then `copyItem` in per-file `do`/`catch`; and the picker configuration, `activePicker` retention, four `@objc` callbacks with `outcomeDelivered` suppression and `Task { @MainActor in }` hops are all untouched.

`declareAllCores` deliberately leaves a core with no dylib undeclared, so a later tap reads nil from the registry, takes the reload path and names the missing file rather than failing inside the loader, and the new `cores:` HUD line makes a partial bundle visible before any tap.

### The BIOS line moved and its comment did not

Before this change, `surfaceAttached` called `ensureCoreLoaded()` unconditionally, which called `biosStatus(in:)` and populated the `bios` HUD line at attach. Now `surfaceAttached` calls `declareAllCores()`, which never writes `bios`, and the only remaining writer is line 646 inside `ensureCoreLoaded`. The BIOS/HLE readout therefore appears only after a user taps a PS1 disc and its core loads, which is after the point where knowing a BIOS is absent would have changed what they did. The `@Published var bios` doc comment still asserts the old behaviour: "Populated the moment the system dir is known, so a missing BIOS is a legible condition rather than a silent drop in compatibility." One of the two has to change.

The line also stopped identifying itself. `biosStatus` prefixes the core id onto the no-system-dir branch only; the two branches that actually run on a device return bare `"BIOS: scph1001.bin"` or `"BIOS: none, HLE fallback"`. Since the line is cleared to empty whenever a cartridge core loads and repopulated when pcsx_rearmed loads, its appearance and disappearance are core-dependent while its text is not.

### What the verification actually covers

No Rust changed, so the 74 and 84 passing tests confirm the engine still builds and behaves, not that this change works. Everything specific to the change is verified by `bash -n`, YAML and plist parsing, `swiftc -frontend -parse` (a parse, not a type-check, with the UniFFI facade absent), and a hand-run stubbed-copy harness proving the four web core names and `all` still reach the WASM path.

Not tested, and testable here: that the five names in `project.yml`, `ios.yml` and `CoreCatalog.library` match `build-core.sh ios-names`. Making `ios-names` host-independent was what enabled this check, and it is a few lines of shell against three greps. Also not asserted anywhere: that `CoreCatalog.routes.keys` and `launchableExtensions` are the same set, which is true by construction today but held together by a comment, so adding an extension to `importableExtensions` without a route would produce a Library row that reports "no core is mapped" only when tapped.
